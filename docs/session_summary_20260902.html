Concept Study

EP1 vs. Site Engine for Fabric Orchestration

Resumed the paused Fabric Extend thread via a new angle — the management plane, not tunnel CLI. Scenario: SD-WAN/IPE connects to a VOSS switch acting as a BEB inside a colleague's network, managed by Site Engine.

  • Site Engine has the documented native depth — persona switch (Switch Engine → Fabric Engine OS), topology config, L2VSN/L3VSN + I-SID config, DVR + redundancy (VRRP/RSMLT/DVR), port templates, and visualization of IS-IS areas / Fabric Connect links / service location. No KB source shows a dedicated EP1 BCB/BEB or I-SID/VSN provisioning workflow — EP1's fabric story today is visualization + AI-assisted workflows on top of Fabric Connect's built-in automation.
  • No requirement to run both — three supported modes: Site Engine only (air-gapped, license-proxy option), EP1 only (cloud/SaaS), or connected mode for phased migration. Switching air-gapped ↔ connected is a few clicks, no hardware or subscription change.
  • New FE addressing detail: SD-WAN allocates a /29 subnet per site from the Fabric Extend IP network, and IPEs use LLDP to hand fabric switches their IP/gateway + destination IPs to auto-build the VXLAN tunnels — FE tunnel addressing is SD-WAN-automated, not manually configured on the switch in this model.
Open, Unconfirmed Exactly how Site Engine reaches a remote BEB switch's management IP behind SD-WAN/IPE — in-band over the same FE tunnel, or a separate OOB path — is not stated explicitly in any retrieved KB source. Flagged for a docs/GTAC follow-up, not guessed at.
Status Concept/mental-model study only — no hardware touched, no build requested. Continue only when asked.

Hypothetical / Consulting Narrative

EP1-Only Cisco→Fabric Hub-and-Spoke Hospital Migration

A client-facing narrative, not lab hardware: HQ + many remote sites, migrating from Cisco, EP1-only (no Site Engine), CLI builds core + BEB, EP1 takes over ongoing management.

  • Extreme's own hub-and-spoke Fabric Extend reference architecture is built around Site Engine / "Fabric Extend Manager," not EP1 — going EP1-only likely means CLI also carries the FE tunnel build, not just BCB/BEB/VSN config.
  • Confirmed this session: the hospital has dedicated circuits (MPLS/leased line) to every remote site. On a private WAN, VXLAN-only Fabric Extend is fully sufficient — IPsec is not required, so the pricier Fabric IPsec Gateway appliance drops out of the design entirely. Any Fabric Connect-capable switch (5320/5420/5720/7520/7720 family) can serve as the branch-side tunnel endpoint directly.
  • Cisco migration can be phased — EP1 + Third-Party Management Engine (TPME) can manage existing Cisco gear centrally alongside the new fabric during transition.
  • Healthcare proof points available as case-study backup: Concord Hospital (zero-downtime bridged cutover), CHU Besançon (security + continuity), ZOL (schedule confidence, segmentation). SPB fabric failover is sub-200ms — relevant for life-safety system reconvergence tolerance.
Status Scoped as a hypothetical/consulting narrative only. No CLI executed, no hardware project created.

Migration Mechanics

RS1 Single-Remote-Site Cutover + Sequencing

Scenario: cut over one BEB at RemoteSite1 plus new EN APs, no NNI at that site yet, uplink runs to dedicated WAN or internet back to a Cisco Core at HQ.

  • Cisco-side config is ordinary, not fabric-aware — KB confirms the third-party core "does not participate in Fabric or Fabric Attach signaling," needs only a conventional 802.1Q trunk (or routed peer) with matching VLAN IDs, same as bringing up any new vendor switch.
  • Two separate things on the RS1 box: (1) SPB/IS-IS/BVLAN + I-SID-to-port bindings — valid to configure even with zero NNI neighbors, dormant until a peer exists; (2) the WAN-facing uplink to Cisco HQ — a plain UNI/legacy-edge VLAN-tagged port, unrelated to the BVLAN/IS-IS config.
  • No universal sequencing rule — KB validates both edge-first (replace one switch with legacy uplinks, then chain outward) and parallel-core (build the new fabric core alongside the existing one, migrate access/gateways gradually) patterns. Recommendation: treat RS1 legacy-edge cutover and the EN_Fabric_Core lab POC as parallel, non-blocking tracks.

Fact-Check

IQController vs. IQEngine, and a PPSK/I-SID Claim Under Scrutiny

  • IQEngine = the AP operating system/firmware persona (formerly HiveOS), not a management platform.
  • IQController / XIQ-C = a separate, centralized on-prem controller platform (airgap licensing, tunneling, integrates with Site Engine/ExtremeControl/ExtremeAnalytics/AirDefense) — a different product line from cloud-managed EP1/XIQ entirely.

Live Hardware Session

KhKLab-SW-01 — FE / NNI / Fabric Attach, All Three Live at Once

Topology confirmed live: port 1/1 → SD-WAN appliance → RDU-Core (FishBowl-Fabric_Core-5720-01); port 1/10 → direct NNI → SW2 (5320-16P-2MXT-2X-FabricEngine); ports 1/3 and 1/7 → AP3000s.

Fabric Attach Qualification

Neither the SD-WAN/FE link (1/1) nor the SW1↔SW2 NNI (1/10) is Fabric Attach — both are genuine Fabric NNI / SPBM IS-IS adjacencies between fabric-native devices. FA only qualifies on the AP-facing ports, 1/3 and 1/7.

Root-Cause Diagnosis: AP3000 Not Getting Proper FA Mapping

  1. show fa elements initially showed STATE T / D (Tagged / AutoConfig Disabled) on both 1/3 and 1/7, despite successful discovery + auth.
  2. Fix applied: fa port-enable 1/7 and fa port-enable 1/3. Confirmed via show fa interface port X — SERVER STATUS flipped to enabled.
  3. Real confirmation: show fa assignment showed both ports with active, client-origin I-SID assignments — FA mechanically working end-to-end (discovery → auth → auto-provision).

Commands That Proved the 3-in-1 Demo

show interfaces gigabitethernet auto-sense 1/1-1/10
  # 1/1 = SD-WAN, 1/10 = NNI-ISIS-UP, 1/3 = FA, 1/7 = FA

show isis adjacencies
  # SD-WAN-1 -> FishBowl-Fabric_Core-5720-01 (Fabric Extend, uptime 05:46:06)
  # Port1/10 -> SW2 (plain NNI, uptime 00:55:16)

show isis lsdb
  # 14 LSP entries across 5 systems in HOME area:
  # TSLab-SW-01, SW2, KhKLab-SW-01, FishBowl-Fabric_Core-5720-01, Fishbowl-SW-01

show isis spbm
  # SMLT-SPLIT-BEB: primary, all-zero virtual B-MAC, no peer system ID
  # (default/inactive SMLT state — unrelated to this demo, not a concern)
Result Fabric Extend, a plain fabric NNI, and Fabric Attach were all captured live and working simultaneously on one switch — the cleanest single-session proof yet that FE and a local NNI are both just IS-IS adjacencies to the fabric, with FA layered on top for non-SPB-capable edge devices.

Open Issues

Two Threads Carrying Into Next Session

1. I-SID Mismatch Across FA Ports show fa assignment shows 1/3 → I-SID 143154 (VLAN 154, generic name ISID-143154) vs 1/7 → I-SID 144154 (VLAN 154, named BOBKit-4-WirelessUser-isid). Same VLAN tag, two different I-SIDs — since I-SID is the actual fabric isolation boundary, these two APs are landing in separate, non-communicating VSNs despite sharing a VLAN number. Likely cause (inference, not KB-confirmed): the two APs are bound to two different EP1 Network Policies/VLAN Profiles, each independently specifying its own Fabric-Attach I-SID for "VLAN 154." Waiting on confirmation of intent — shared single VSN for roaming vs. deliberate per-AP isolation — before prescribing an EP1-side fix.
2. AP on Port 1/7 Went Down Reported at session end — link/physical state, not the FA mapping issue above (that AP was FA-active moments earlier in this same session). No diagnostic commands run yet. Next step: show interfaces gigabitethernet 1/7 (or equivalent port/link-state command) plus current show fa elements / show fa interface port 1/7 to determine whether this is a physical link-down, a PoE issue, or an FA state regression.
