  • IP forwarding verified live on 5320-16P-2MXT-2X-SwitchEngine — show ipconfig vlan Default and show vlan Default both confirm forwarding is enabled and working, even though show config | i ipforwarding didn't surface a matching line.

Investigation

"show config | i ipforwarding" Showed Nothing — False Alarm

Ran enable ipforwarding vlan Default on the switch, then checked for it with show config | i ipforwarding. No match. Rather than guess at why, verified against live runtime state instead of the config-diff view:

show ipconfig vlan Default

Router Interface on Default is enabled and up.
    inet 192.168.0.28/24  broadcast 192.168.0.255  Mtu 1500

    Flags:
        BOOTP Host  NO   DirBcstHwFwd  NO          Fwd Bcast  NO    IgnoreBcast YES
         IP Fwding YES       IPmc Fwd  NO   Multinetted VLAN  NO    IRDP Advert  NO
        Send Redir YES           VRRP  NO TCP Adjust MSS OFF

show vlan Default

IPv4 Forwarding:     Enabled
IPv4 MC Forwarding:  Disabled
Primary IP:          192.168.0.28/24
Conclusion IP forwarding was enabled and functioning the whole time. The grep miss against show config is a display-format quirk on this EXOS build — not evidence the command failed. Runtime state (show ipconfig / show vlan) is the authoritative check, not a filtered config dump.

Root Cause

The Real Problem Was on the AP — ETH0 Uplink Set to Trunk in EP1

With the switch cleared, the actual source of the session's connectivity confusion turned out to be the AP, not the 5320. The AP's ETH0 uplink port mode was set to Trunk in the device-level setting inside EP1. Correcting the uplink mode resolved the issue.

Lesson A switch-side investigation (grep misses, config visibility) can be a red herring when the real misconfiguration lives one layer up, on the AP's own device-level EP1 setting. Don't assume the switch is the source of the problem just because that's where symptoms first showed up — check the AP's EP1 device-level uplink port mode (Access vs Trunk) early in the sequence.
