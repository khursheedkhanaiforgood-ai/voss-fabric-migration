Port Verification

Confirming Ports 1 & 3 Are Untagged-Only

Two commands confirmed the port plan before any policy push:

show vlan Default

Ports:   20.  (Number of active ports=2)
   Untag:  *1, 2b, *3, 4b, 5b, ...

Everything listed sits under the single Untag: heading — no separate Tagged: list exists at all. * = active; b = blocked/unused. Ports 1 and 3 are both active, untagged, Default-VLAN-only.

show ports 1,3 information

Port 1: Num VLAN = 1
Port 3: Num VLAN = 1

Each port belongs to exactly one VLAN. If UZTNA_10 were tagged onto either port, this would read 2. Confirms zero VLAN leakage.

Clarified — L2 Switching vs IP Forwarding vs Port Forwarding Client-to-home-router traffic on Default VLAN is pure Layer 2 bridging (both ports untagged, same broadcast domain) — no routing, no enable ipforwarding needed. That command only matters later, when UZTNA_10 traffic has to cross into Default to reach the internet. "Port forwarding" as a per-port toggle doesn't apply here at all; the relevant flags (f/M/B flooding, Layer 2 Forwarding Enabled) were already on by default.

CAPWAP Troubleshooting

"AP Loses CAPWAP / Reverts to Default" — Investigated

This symptom recurred from a prior VOSS session. Worked through two documented EP1/ExtremeCloud IQ mechanisms:

TheoryMechanismVerdict
CAPWAP rollback timer If the AP can't reconnect to its CAPWAP server within 15 minutes of a policy-push reboot, it auto-rolls-back to the previous config and reboots again. Ruled out — CAPWAP reconnects fine every time
Device-level override Settings under Manage → Devices → <device> → Configure override the network policy template for that device only, until explicitly cleared. Ruled out — no device-level config present on AP_3000_MyLab
Resave + redeploy required Some network-policy changes reportedly need a second save cycle and an explicit redeploy (or a "Complete Configuration Push" that writes the full startup config) before they take effect. Not yet tested — leading theory for next push
Firmware Check Needed Before Next Push WPA3-802.1X requires AP3000 IQ Engine ≥8.4r8; Direct Tunnel (vs. Legacy Proxy) requires IQ Engine ≥10.8.7. If the AP is below either threshold, EP1 silently withholds the SSID rather than erroring — which can look identical to a "revert." AP3000's current firmware version was not confirmed this session.

UZTNA Design Decisions

EAP-TLS vs EAP-TTLS, and Open+CWP vs 802.1X+CWP

Auth Method — Landed on EAP-TTLS

EAP-TLSEAP-TTLS (chosen)
Client cert required Yes — every device needs one issued No — username/password only
Backing infrastructure Platform ONE Security native cloud PKI (confirmed available without external IdP, but flagged as a possible add-on subscription) Local user directory in Platform ONE Security
Why chosen — Explicit requirement: no certs to be supplied/distributed to client devices

SSID Security Type — Enterprise 802.1X, not Open

Corrected Assumption Plan was "keep SSID Open, add a CWP for username/password." Extreme's own documentation states a RADIUS-authenticated CWP requires the SSID to be Enterprise 802.1X — Open SSIDs cannot carry a RADIUS-backed CWP. Kept the SSID as Enterprise 802.1X (already configured) and layered the CWP on top, rather than switching to Open.

User → Group → VLAN Resolution Chain

  1. Client authenticates (EAP-TTLS username/password, or CWP browser login) against the AP's RADIUS Server Group UZTNA-RadsecServerGroup
  2. UZTNA backend validates the individual local user's password
  3. UZTNA resolves that user's group membership (e.g. Policy_TeamUSA)
  4. Access-Accept returns Filter-Id = Policy_TeamUSA
  5. SSID's User Access Settings assignment rule maps that Filter-Id to VLAN UZTNA_10
  6. AP tags the client's traffic accordingly on its uplink port — which requires the switch to actually have UZTNA_10 tagged on that port and DHCP running, neither of which is live yet
